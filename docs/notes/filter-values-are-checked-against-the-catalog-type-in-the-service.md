A filter value is checked against the catalog's column type in the service, not in the planner, because only the service has the catalog.

The planner is a pure function of the model (definitions) and a request, and a definition does not say that `customer.province` is text, so `customer.province = 5` plans and PostgreSQL answers "operator does not exist: character varying = integer" (C-9). Compiling needs a synced catalog (D-30), so `makna.services.service.compile_on_snapshot` calls `makna.services.filter_types.check_filter_types` after planning with `Snapshot.column_types` (`(engine_fqn, column)` to the catalog `data_type`), and raises `INVALID_FILTER` with the catalog type in `details`. The compile evals call the same function, so they see the same refusals.

It applies only to a dimension that reads exactly one column (no `expr`, or an `expr` that is that column). For any other expression the type of the comparison is not a column's type and nothing is claimed. The table of what fits is `makna.model.values.value_fits_column`: a typed constant (a time dimension's `CAST(... AS DATE)`, a boolean) fits only the matching column types, a number fits the numeric types, and a text constant is read by PostgreSQL as the type of the column, so it must be written the way that type is read (`'5'` fits an integer column, `'5.5'` does not). The refusal never repeats the value of a personal dimension.
