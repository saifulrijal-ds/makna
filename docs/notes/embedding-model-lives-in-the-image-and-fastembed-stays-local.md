Download the embedding model when the image is built and let fastembed read only local files at run time; prove "no network" with a stack on an `internal: true` network, not with a unit test.

Seen while building WP-07 (2026-11-11). Checked in the installed `fastembed` 0.9.1 source, not by running the real model (Hugging Face was blocked in the session).

- `TextEmbedding(model_name, cache_dir=..., local_files_only=True)` resolves the files from `cache_dir` and never downloads; `HF_HUB_OFFLINE=1` has the same effect. Without `cache_dir` it uses a temp directory, which an image would not carry. The class method `TextEmbedding.get_embedding_size(model)` gives the dimension (384) without loading the model, so `index build` that has nothing to embed never loads it.
- `deploy/Dockerfile` downloads the model into `/opt/makna/models` right after the dependency layer and before `COPY src` and `COPY config`, so editing code or settings does not fetch 0.22 GB again; a test keeps the Dockerfile and `config/makna.toml` in agreement.
- The test tier never touches the model: the fastembed contract test replaces `fastembed.TextEmbedding`, and `tests/conftest.py` sets `HF_HUB_OFFLINE=1`. The real model (384 dimensions, deterministic, "pembiayaan bermasalah", p95 under 500 ms) is checked only by `deploy/check_search.py` in the CI stack job.
- A running stack's network cannot be switched to `internal`, so the offline proof is a second project (`docker compose -p makna-offline -f ... -f deploy/docker-compose.offline.yml`) built from the same image; an internal network publishes no ports, so its checks run with `exec` in the app container.
- Reminder for packages that run a real model: `httpx` was a dev dependency, and the image installs with `--no-dev`; anything the runtime imports belongs in `dependencies`.
